# I-12 — A third op category the server relays but never stores

- **Improvement ID:** I-12
- **Version:** 0.9.0
- **Date:** 2026-07-28
- **Status:** ✅ DONE (542 tests; live-verified).
- **Related work:** the build_begin precedent from P-12 (I-6); consumed by the next three phases

## Objective

Give the protocol a vocabulary for directing presentation, so an agent can say 'view 1' or 'rotate on' at all. Five explicit ops rather than one grouped op, because the Go client requires every declared field to be present. Move the VIEWS table to packages/shared/views.js so the server can range-check n instead of letting an out-of-range view be a silent no-op.

## Approach

New `packages/shared/views.js` holds the `VIEWS` table lifted from `CameraDirector.js:11-18` plus
`VIEW_COUNT` — plain data, no three.js import, so `protocol.js` can import it the way it already
imports `config.js` and `materials.js`. That is what lets the *server* refuse `n: 7`; today the
table is module-scoped and unexported, so an out-of-range view returns `ok:true, sent:1` and does
nothing — indistinguishable from success to a blind agent.

`protocol.js` gains `VIEWER_OPS` + `isViewerOp` beside `PART_OPS`/`CONTROL_OPS` (the justification
is routing — the server and `applyLocal` both need one predicate — not taxonomy), an `isBool`
helper, and five `OP_SCHEMA` rows: `view {n:'int+'}`, `reframe {}`, `rotate|grid|hud {on:'bool'}`.
The unknown-op gate widens to test the third set; `view` is range-checked `1..VIEW_COUNT`; the three
flag ops share one validate arm; `reframe` joins the field-less fall-through. The `PART_OPS` gate
that guards material and bounds checks, `expand()`, and `contract()` are all **unchanged** — they
already do the right thing.

`apps/server/commands.js` collects viewer ops into an array via `isViewerOp`, before the `isPartOp`
arm. That array is deliberately **not** reset inside the `clear` arm the way `added`/`removed` are —
a view op is not made moot by a clear. `createServer.js` puts it on the **broadcast only**, not the
ack: `broadcast()` already includes the sender, and the CLI's typed `Ack` drops fields it wasn't
compiled for (it has silently dropped `buildBegin` since P-12).

The ordering rule goes in the `protocol.js` header, because it is a real semantic and not an
accident: viewer ops apply **after** the world diff regardless of batch position, so
`[{view:1}, box, clear]` lands as `clear → box → view`.

## Verification

`npm test` — 109 passed / 8 files, of which 14 are new here. `npm run build` succeeds, which is what
proves the `@codeblox/shared/views.js` import resolves through Vite's alias and not only under
vitest.

The claim worth pinning is the range check: `validate({op:'view', n:7})` now returns
`ok:false, errors:['n must be an integer 1..6']`, where before P-15 there was no `view` op at all and
`CameraDirector.viewFrom(7)` returned `null` into a caller that discarded it.

`applyLocal` in `main.js` was deliberately left alone — its `isPartOp` guard means a viewer op
validates and is then ignored offline. Making it act is I-13.
