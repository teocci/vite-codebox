# I-14 — A view verb group, and a real bool field type in the contract

## Objective

Presentation is not a build verb and does not belong in an exec batch — exec is the batch runner. Give it its own group the way auth has one. Implement bool in the Go client rather than deferring it as axis is deferred: axis defers because its value domain is server data, while bool is a structural JSON check, and deferring it means a bad flag lands all the parts in the batch and silently skips the rotate.

## Approach

A new `dispatch_view.go` holds the group, following `dispatchAuth`/`dispatchBuild`: `codeblox view
<1-6>` (a numeric argument is a preset, a word is a subcommand), `view reframe`, and
`view rotate|grid|hud on|off`. It reuses `flagSurface`, the existing session path, `--json` and
`--dry-run`, and rejects unknown subcommands and stray arguments the way I-1 established.
`dispatch.go` gains the routing arm and the usage text. The filename suffix `view` collides with no
`GOOS`/`GOARCH`, so it carries no implicit build constraint.

The group exists because presentation is not a build verb. `exec` is the batch runner — it parses a
JSON array, object or NDJSON and validates the whole batch before sending — and routing camera and
HUD direction through it is a category error. The CLI's own convention already says so: `clear` is
an op *and* a verb, as are `box`, `sphere`, `cylinder` and `remove`.

`contract.go` gets `typeBool` and a `checkField` case, about six lines. This is deliberately **not**
the `axis` deferral: `axis` defers because its value domain (`x|y|z`) is server data the client
refuses to compile in, whereas `bool` is a structural JSON check fully described by its type name,
in the same category as `int+` and `id` — both of which are implemented. The reason it matters is
failure behaviour, not tidiness: `applyBatch` records a rejected command in `errors` and continues,
so `[...30 parts..., {op:'rotate',on:'yes'}]` would land all thirty parts and silently not rotate,
with the error buried in an ack the CLI drops. Client-side rejection kills the batch before anything
is sent, exit 5.

`view.n` stays `int+` on the Go side — a `'view'` type would compile in "there are six presets",
precisely the server knowledge this package refuses to hold. A test asserts `n: 7` produces **no**
client-side error, so nobody later "fixes" it by hardcoding the count; the server refuses it.
