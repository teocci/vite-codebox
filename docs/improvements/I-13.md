# I-13 — Route viewer ops around the block engine, and let an agent-set view survive the build

- **Improvement ID:** I-13
- **Version:** 0.9.0
- **Date:** 2026-07-28
- **Status:** ✅ DONE (542 tests; live-verified).
- **Related work:** depends on the ops published by the previous phase

## Objective

Make the five ops actually do something, without threading presentation state through World.js. Convert every toggle to an idempotent setter, since an agent is blind and cannot read viewer state back. Add hold to viewFrom/setRotate so an agent-set angle is preserved and refit as the build grows, rather than flipping to USER mode and silently disabling framing for the remaining stages.

## Approach

`WsClient` gains `onViewer` in the same options bag as `onStatus`, which is already the shape for
"report something that is not world state via an injected callback". It fires **after**
`world.applyDiff` in the `'diff'` case — that statement's position *is* the ordering rule, so it
lives in exactly one place and is testable. Threading five presentation ops through
`World.applyDiff` was rejected: `World.js` is the block engine, and it would gain parameters it
neither reads nor validates. `buildBegin` is one wart, not a pattern to extend.

`main.js` wires `onViewer` to `viewer.applyViewerOps`; `applyLocal` collects a `viewerOps` array
(the name `viewer` is taken) and dispatches it after `applyDiff`, keeping the offline path in
lockstep; `driver` gains the five methods for console parity.

Every toggle becomes an idempotent setter, because an agent is blind — viewer state is not in
`world_info` and there is no read-back channel. `Grid` gets `set visible` paired with its existing
getter, `Hud` gets both, and `toggle()` delegates in each, keeping its current return contract.
`Viewer.applyViewerOps` dispatches to those setters; the four keyboard paths delegate too, each
keeping its toast. `reframe` routes through **`Viewer.reframe()`**, not `CameraDirector.reframe()` —
only the Viewer method clears `_focusIds`, and skipping it leaks the focus group so the framer keeps
chasing a stale build.

`CameraDirector` gains `setRotate(on, {grab})` with `toggleRotate()` delegating, and `{hold}` on
`viewFrom`. `hold` is the mechanism that makes "set view 1, then build" work: `viewFrom` forces
`mode='user'` because for a human pressing `1` it genuinely is a handoff, but for an agent it is
not. Since `tick()` re-derives the direction from the camera's current position each frame and
corrects only distance and target, an angle set in agent mode is **preserved and refit** as the
build grows — so every stage lands framed at that angle instead of stages 2..N silently falling out
of frame. `engageAgent()` keeps a deliberately-set view name rather than reverting the HUD label to
`auto` while the angle persists.

`controls.js` and the `Hud` hint stop hardcoding `1-6` and derive it from `VIEW_COUNT`.

## Verification

`npm test` — 10 files, 130 tests, 16 new. `npm run build` clean.

Two claims are worth more than the count.

**`hold` actually refits.** The test grows the world's bounds radius 10× after an agent sets view 1,
runs 60 frames of `tick`, and asserts the viewing angle is unchanged (`angleTo < 1e-3`) while the
camera distance grows past 5×. Its companion asserts the *old* behaviour is still what happens
without `hold`: distance unchanged to three decimals, because USER mode means no refit at all. That
pair is the improvement — one test alone would not show that anything changed.

Writing it surfaced a real subtlety: `_framedBounds()` floors at `MIN_RADIUS_METRES`, so at small
radii the framer fits the floor rather than the build and no growth ratio is observable. The first
version of the test asserted 5× growth over radii that were both under the floor and failed at
exactly 4×. The radii moved above the floor; the code was right.

**The ordering rule is pinned where it lives.** `WsClient._onMessage` is tested directly with
`vi.stubGlobal('location', …)` and a fake world that logs — `connect()` is never called, so no
WebSocket is needed — asserting the log reads `['diff:1', 'viewer:view']` and never the reverse.

**Live, against the running server** (`npm start`, ws on 7799): the contract publishes all five ops;
a batch of `[{view:4}, box, {rotate:true}]` came back with `diff.viewer` carrying both viewer ops and
the box in `added`; `{view:99}` was acked `n must be an integer 1..6` with `diff.viewer` empty. That
also confirms the running server was not stale — the failure mode where an op exists in `protocol.js`
but not in the process actually serving it.

Not verified: that the browser *visibly* snaps and holds. The relay was confirmed to the browser
boundary and the camera math is unit-tested, but no headless browser runs in this repo.
