# F-1 — CLI bricks at ~330 parts, including clear

- **Fix ID:** F-1
- **Version:** (pending)
- **Date:** (pending)
- **Status:** 🚧 IN PROGRESS
- **Related work:** blocks every phase in R2 — a true-scale car is ~90 parts and a building ~200

## Symptom

Past roughly 330 parts, every codeblox command fails at the handshake with ErrMessageTooBig — including the clear that would recover the world. Nothing short of restarting the server helps, and `codeblox info` keeps reporting a healthy server from its cache while every build fails.

## Root cause

`transport.Dialer.Connect` never called `ws.SetReadLimit`, so `coder/websocket`'s `defaultReadLimit` of 32768 bytes (`read.go:107`) applied to every frame the CLI read. The first frame it reads is the welcome, and `apps/server/createServer.js:53` builds that as `{type, contract, parts: store.snapshot()}` — **the entire world**. So the frame the CLI must read to do anything at all grows with the build.

Measured against the plans in `builds/`: a zero-part envelope is 5349 bytes, and a part serialises to 79.6–86.8 bytes depending on material-name length and coordinate width.

| build | parts | welcome bytes | bytes/part | break point |
|---|---|---|---|---|
| tesla-model-s | 36 | 8240 | 80.3 | 341 |
| white-house | 31 | 8040 | 86.8 | 315 |
| golden-gate-bridge | 52 | 9749 | 84.6 | 324 |

Every server-touching verb dials through the same path (`command/app.go:103` → `:138` → `Dialer.Connect` → `handshake` → `ws.Read`), and `dispatch.go:94` routes `info`, `materials`, `exec`, `box`, `sphere`, `cylinder`, `remove` and `clear` through it. So the recovery command dies with the rest.

Two things made it worse than a plain failure. There is no partial undo — `remove` takes an id, not a region — so `clear` is the only way back, and it was equally dead. And `codeblox info` without `--refresh` serves the cached contract from `~/.codeblox/world_info.json`, so `doctor.py` and `world.py` kept reporting a healthy server while every build and every clear failed.

It had never been hit because the largest build in `builds/` is 52 parts. Building at true scale is what would have found it: a 1:1 car is ~90 parts and a building ~200, so two builds cross the cliff.

## Fix

One line in `Dialer.Connect`, after the dial and before the handshake:

```go
ws.SetReadLimit(-1)
```

`-1` disables the limit rather than raising it, because any fixed ceiling is the same bug with a larger constant — the frame is O(world), so any limit is a part count in disguise. The server is trusted and local (`CheckTransportSecurity` already refuses to put a token on a plain `ws://` link to a non-loopback host), so the welcome frame is not a hostile-input surface. The comment at the call site names the welcome-snapshot reason, so the next reader does not "tighten" it back.

The deeper fix — not shipping the full snapshot to a CLI that discards it, since `Conn` exposes only `Contract()` and nothing ever reads `Welcome.Parts` — is a protocol change and is deliberately out of scope here.

## Verification

The test builds an 83624-byte welcome (1000 parts) and asserts both that `Connect` succeeds and that all 1000 parts survive the round trip — the second assertion is what would catch a silent truncation rather than an error.
