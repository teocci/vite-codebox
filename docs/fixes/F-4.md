# F-4 — The HUD extent row overflows the panel at 1:1 scale

- **Fix ID:** F-4
- **Version:** 0.9.0
- **Date:** 2026-07-28
- **Status:** ✅ DONE (542 tests; live-verified).
- **Related work:** I-10 (P-11) — the same class of defect, viewer literals tuned for the 64 m world that shipped before it; the scale gate from I-8 (P-9), which is why the metre value must stay exact

## Symptom

The HUD's `extent` row carries both unit systems in one value. At the 1:1 scale P-9 made the point
of the project, the Golden Gate build renders

```
extent   136850×11350×136850 blk · 2737×227×2737 m
```

— 41 monospace characters in a single value. `.hud` sets `min-width: 15rem` but no `max-width`, so
the panel grows across the viewport. The failure appears only at the scales P-9 and P-11 exist to
make possible.

## Root cause

Two independent things, both dating from the 64 m world that shipped before P-11.

The row was written to carry both unit systems because at 64 m both triples were short and the
combined value still fit. P-9 and P-11 then made 1:1 builds the point of the project without
revisiting it — and since `BLOCK_SIZE` is `0.02` the block triple is **by construction** 50× the
metre triple, so once one is large the other is too. The two can never both be short again.

Underneath that, `.hud` has a `min-width` and no upper bound, so nothing stops a long value from
pushing the panel to any width. The row is what trips it; the missing cap is why there is no floor.

Same class as I-10: viewer literals tuned for a world size that no longer ships.

## Fix

Two rows instead of one, and a cap.

`extent` now carries metres alone and a new `blocks` row carries the integer triple. Splitting is the
only move that survives the arithmetic: `BLOCK_SIZE` is `0.02`, so the block triple is *by
construction* 50× the metre triple, and any single row must hold both once either is large.

The separator became `' × '` from `'×'`. That is not cosmetic — it is what creates the break
opportunities. `136850×11350×136850` is one unbreakable word to the line-breaker, so no `max-width`
could contain it; spaced, the triple wraps at its separators and the row shrinks to fit. `.value`
gained `min-width: 0` so the flex item is allowed to shrink to that wrapped width instead of holding
its `min-content` floor.

`.hud` gained `max-width: 20rem` beside its existing `min-width: 15rem`. The panel is a legend, not a
document; bounding it is what makes the failure impossible rather than merely less likely at the next
scale.

Abbreviation was rejected, not overlooked. `2.7k m` cannot be compared against a real subject's
2737 m, and comparing against the real subject is precisely what the I-8 scale gate is for — so the
metre row is load-bearing and every digit stays. The width problem is a layout problem and is solved
in the layout.

The two formatters were lifted out of `update()` as exported pure functions so they are testable:
`environment: 'node'` in `vite.config.js` means there is no DOM to assert against, and the string is
the part that can regress.

## Files changed

| File | Change |
|---|---|
| `apps/web/src/viewer/Hud.js` | `extentMetresText` / `extentBlocksText` exported as pure formatters; the `extent` template row split into `extent` + `blocks`; `update()` writes both. Header comment records why one row cannot work. |

## Verification

`npm test` — 9 files, 114 tests, of which 5 are new. `npm run build` clean, and `max-width:20rem` /
`min-width:0` are both present in the emitted `dist/assets/*.css`, so the rules survive the CSS-module
pipeline rather than only existing in source.

The before/after on the case from the Symptom:

```
before   extent   136850×11350×136850 blk · 2737×227×2737 m     (41 chars, one value)
after    extent   2737 × 227 × 2737 m                           (19 chars)
         blocks   136850 × 11350 × 136850                       (23 chars)
```

**Not visually confirmed in a browser this session.** The formatter strings and the presence of the
CSS rules are verified; that the panel *renders* bounded at 20rem is inferred from the rules, not
observed. The repo carries no headless-browser tooling and adding one is chore-track work, outside
this fix.
